# AI Agent Team Orchestrator — V2 "Artifact-First"

## What This Is

An AI-powered autonomous agency for **code delivery**. Users write a brief, a cross-functional team of specialized AI agents (leads + workers) collaborates to produce the code, and the user reviews and iterates through version-controlled diffs.

**One-liner:** *You write the brief. We deliver the code. You review the diff.*

**Scope:** Code-only. All templates produce code artifacts. Prose/content templates are not actively maintained.

## Architecture — Key Decisions

Locked decisions from the TDD process. Do not change without explicit approval.

- **AD-1:** Single-tenant MVP. All tables have `workspace_id` FK. Hardcoded `workspace_id = "1"`.
- **AD-2:** Celery + Redis for execution (not Temporal).
- **AD-3:** One orchestrator Celery task per execution. `asyncio.gather` for parallel waves.
- **AD-4:** Agent skills in database (not S3). 8k token budget (6k skills + 2k learnings).
- **AD-5:** Multi-file artifacts: S3 directory + JSONB `file_manifest` on `ArtifactVersion`.
- **AD-6:** Diffs computed on-the-fly by frontend. No diff storage.
- **AD-7:** pgvector for uploaded documents only (not agent skills).
- **AD-8:** Hardcoded DAG templates + LLM router. **13 code-focused lead-guided templates** (Sprint 13). Lead templates are fixed; worker specializations are Haiku-generated at onboarding.
- **AD-24:** Lead-guided execution model. Every template has: planning waves (leads analyze + delegate), execution waves (workers implement), review wave (leads APPROVE / MINOR_FIX / REVISE). Max iterations per template (default 3).
- **AD-25:** Agent role: `lead` | `worker`. Leads assigned to planning/review slots; workers assigned to execution slots. Roster generated by Haiku includes both types.
- **AD-26:** Template-specific review grading criteria. Each template defines `review_criteria` — a PASS/FAIL checklist injected into review prompts.
- **AD-27:** Delegation validation. Optional wave between planning and execution validates plan specificity (on 4 complex templates). Max 1 re-plan.
- **AD-28:** Mid-loop context summarization. Haiku compresses accumulated messages when they exceed 60K tokens (configurable). Checked every 3 iterations.
- **AD-29:** `code_exec` tool for review phase. Sandboxed shell execution in temp dir (30s timeout, no network on Linux, sensitive env vars stripped).
- **AD-30:** Execution telemetry. Structured JSON logs for agent runs, review loops, compaction. All agent limits centralized in `settings.py` as env-var-tunable parameters.
- **AD-14:** GitHub/GitLab auth via PAT only (no OAuth for MVP).
- **AD-15:** Artifact files served via backend proxy (not pre-signed URLs).
- **AD-16:** Cursor-based pagination on all list endpoints.
- **AD-19:** Fresh design system. oklch colors.
- **AD-23:** Both light and dark mode from day one.

## Core Domain Model

- **Artifact** = a deliverable (not a task). States: `drafting` → `in_review` → `approved` (+ `cancelled`).
- **ArtifactVersion** = immutable version. S3 file bundle + JSONB manifest.
- **ExecutionWave** = one execution run. `dag_plan`, `assembled_team`, heartbeat fields.
- **Agent** = persistent AI entity in the roster. Skills, learnings, readiness score.
- **AgentSkill** = knowledge entry. Categories: `skill`, `work_learning`, `briefing`.

## Change Workflow

Every change must follow this process:

### 1. Read the relevant TDD first
Before touching any code, read the TDD section(s) that cover the area being changed:
- New/changed endpoint → `04_API_AND_INTEGRATIONS_TDD.md`
- New/changed DB model or migration → `02_BACKEND_ARCHITECTURE_TDD.md`
- New/changed agent behavior, tool, or prompt → `03_AI_AGENT_ENGINE_TDD.md`
- New/changed UI route or component → `05_FRONTEND_UX_TDD.md`
- New/changed user journey or state machine → `01_PRD_AND_WORKFLOWS.md`
- New sprint or tickets → `06_IMPLEMENTATION_ROADMAP.md`
- New architectural decision → `CLAUDE.md` (AD-X list)

### 2. Update the TDD before implementing (for features)
For new features or significant changes: update the TDD to spec the change first, then implement against it. For bug fixes or minor tweaks, update the TDD after.

### 3. Implement and test
Make the code change, then run `pytest tests/ -v` to verify nothing broke.

### 4. Keep TDDs in sync
After every session that changes code, update any TDD sections that are now stale. The TDDs are the source of truth — they must reflect what is actually implemented.

## Do NOT

- Change architectural decisions (AD-1 through AD-30) without discussion
- Create V1-style task/team/chat models — V2 is artifact-centric
- Add prose/content templates or general task management — this is a **code factory**
- Use OAuth for git providers (PAT only for MVP)
- Store diffs in the database (compute on-the-fly in frontend)
- Add a conversational chatbot interface (this is not a chatbot)
- Use pre-signed S3 URLs (backend proxy only)
